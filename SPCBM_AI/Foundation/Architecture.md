# SPCBM System Architecture

Version: 1.0

---

# 1. Overview

SPCBM is implemented as a Single Page Application (SPA) where the homepage acts as the central interaction workspace.

Rather than navigating between multiple pages, users interact with different content domains through dynamic workspace transitions.

The architecture is intentionally designed to preserve user context while minimizing page navigation.

# 5. Hero Workspace

The Hero Workspace is the primary interaction surface.

Responsibilities:

Display Preview

Display Gameplay

Display contextual information

Maintain user focus

Support recursive transitions

The Hero Workspace is treated as a shared application resource.

There must only be one active Hero Player.

---

# 6. Recursive Workspace

SPCBM avoids unnecessary page navigation.

Instead, users move deeper into content while remaining inside the current workspace.

Example:

Homepage

↓

Game Preview

↓

Gameplay

↓

Playlist

↓

Continue Watching

↓

Back to Homepage

The interaction model remains consistent regardless of depth.

---

# 7. Gameplay Engine

The Gameplay Engine manages:

Gameplay launch

Playlist generation

Video progression

Continue Watching

End-of-playlist behaviour

Player state

The Gameplay Engine is responsible for behaviour.

Presentation components should remain unaware of playback logic.

---

# 8. Data Flow

User selects game

↓

GameData

↓

Game JSON

↓

Application State

↓

Hero Workspace

↓

Media Rendering

↓

User Interaction

No presentation component should read JSON directly.

Application logic acts as the intermediary.

---

# 9. State Ownership

Application State owns:

Current game

Current workspace

Current gameplay item

Continue Watching state

Playlist state

Presentation components should render state.

They should not create state.

---

# 10. Media Architecture

Media information is represented by metadata.

Examples:

Preview Video ID

Gameplay Video ID

Gallery Video IDs

Thumbnail

Title

Presentation URLs are generated by the application layer.

Data should remain independent of rendering implementation.

---

# 11. Extension Strategy

Future features should integrate through existing architecture.

Examples:

Marketplace Edition

Engineering Journal

Benchmark Database

Component Explorer

These should become additional workspace types rather than independent applications.

---

# 12. Architectural Invariants

The following rules are mandatory.

• One Hero Workspace.

• One active gameplay session.

• Preserve user context.

• Reuse existing rendering engines.

• Extend architecture before replacing architecture.

• Prefer state transitions over navigation.

• Data remains independent of presentation.
